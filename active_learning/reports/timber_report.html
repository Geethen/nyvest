Timber vs Native Inference

Decision report for the nature-type active-learning app · Vestland, Norway · A40 / Linux · 2026-06-22
Bottom line. Timber's compiled-C inference is genuinely transformative for single-sample latency on scalar-leaf models (we reproduced 850× over XGBoost). But this app's hot paths are batched — ranking a 75k-location pool (~0.1 s) and a 954k-pixel dense raster tile (5.6 s) — and its model is a CatBoost multiclass classifier, which Timber 0.6.0 cannot compile at all (its tree IR has no vector-leaf representation). In the batch regime, native inference is competitive-to-faster even for the models Timber can compile. Decision: native CatBoost  Timber is kept as a pluggable --backend seam for a future single-sample / edge deployment.

1 · The two regimes that decide everything

Timber compiles a tree model to C99 and runs it via a thin ctypes wrapper. The blog post (geethen.github.io) measured an XGBoost binary classifier and made the key distinction explicit:

~12 µs
Python⇄C ctypes bridge cost — paid once per call, regardless of batch size
0.09 µs
Blog's raw compiled tree math (single sample, called from C)

So the speedup you actually get depends entirely on how many samples ride on one bridge crossing:

  • Single sample → the 12 µs bridge is dwarfed by Python/XGBoost's own setup (hundreds of µs to ms). Timber wins enormously. Blog: 64× (Mac/Win); ours: 850× on Linux.
  • Large batch → the bridge cost is amortised to near-zero per sample, but so is the native library's — and an optimised batch predictor (XGBoost 3.x, CatBoost) has no Python-per-row overhead to begin with. The advantage collapses or reverses.

2 · Reproducing the blog: XGBoost binary (scalar-leaf)

This is Timber's good case — a binary classifier whose leaves are single scalars, exactly what the blog tested. We trained the same shape (50 trees, depth 4) on the 64-band AlphaEarth features (class 8 = water, one-vs-rest) and benchmarked on this box.

This confirms and extends the blog. The 850× single-sample win is real and larger than the blog's 64× (Linux's ctypes bridge is cheaper than the blog's Windows box). But in the batch regime the blog reported Timber slightly ahead (0.40 vs 1.61 µs); with XGBoost 3.2's faster batch path, native XGBoost is now ~2.6× ahead of Timber per sample. The crossover has moved further toward "batch ⇒ use native". The 0.098 max-prob error is Timber's threshold quantization, exactly as the blog's timber validate section warns — harmless for argmax/ranking, relevant if you consume raw probabilities.

3 · Our actual model: CatBoost multiclass (vector-leaf)

The app's classifier is a 10-class CatBoost (loss_function="MultiClass"). This is not the blog's case, and Timber cannot handle it:

✗ won't compile
TypeError: 'int' object is not subscriptable at catboost_parser.py:68
160 ≠ 16
A 16-leaf multiclass tree stores 160 leaf values (16×10). Timber's IR holds one scalar per leaf — no vector-leaf representation.

Two distinct blockers, both structural rather than configuration:

  • Parse crash. CatBoost writes scale_and_bias = [1, [0,…]] (scalar scale + per-class bias vector); the parser indexes bias_data[0][0] and hits the int. Affects binary CatBoost too ([1,[0]]).
  • No vector leaves. Even past the crash, multiclass needs per-class leaf accumulation + softmax. Timber's Tree/TreeNode IR and C codegen are single-output. The blog's own "CatBoost multiclass caveat" anticipates this — it is the one combination the blog flagged but did not benchmark. We confirmed it empirically.

We tested the obvious workaround — and it fails on accuracy

Binary one-vs-rest is scalar-leaf, so we patched the JSON ([1,[0]]→[[1.0],[0.0]]) to get Timber to compile a binary CatBoost. It ran, but its output was numerically wrong: max|sigmoid(timber) − P(class=1)| = 0.50 — a leaf-indexing mismatch in Timber's oblivious-tree parser. So even a 10×-OvR Timber map would be corrupt, on top of being slower in batch. workaround rejected

4 · What this app's workload actually costs (native)

The app's live model is native XGBoost (CPU, multi:softprob). It is designed so model scoring never blocks the labeller — the UI reads a pre-ranked queue and rescoring happens in batch. Measured on the A40 box:

Rescore 75k pool (proba)
141 ms
Rescore 75k + APS set-size
157 ms
Fast retrain (15k, 150 it, 1-split)
10.8 s
Dense tile 954k px (class+unc)
5.6 s

Per-sample on the 75k pool: CatBoost multiclass = 1.9 µs/row (10 classes + APS). Dense raster ≈ 170k px/s ⇒ all 154 tiles ≈ 15 min single-threaded.

None of these is single-sample-latency-bound. The one path a user waits on synchronously is the fast retrain (10.8 s), and that cost is CatBoost training, which Timber does not touch — Timber only accelerates inference, which is already 0.1 s.

5 · Synthesis — blog insights × AL-guidance × our findings

From the blog (validated here)

  • The C math is ~90 ns; Python wrapping is the real cost. ✔ reproduced (12 µs bridge).
  • Batch your data to amortise the bridge. ✔ — and at large batch, native catches up.
  • float32 inputs, contiguous. ✔ already how tiles + pool are fed.
  • Skip timber serve (HTTP adds ~2 s/req); use the in-process predictor. ✔
  • Quantization shifts probabilities slightly (≤0.025 in blog; 0.098 here). ✔ ranking-safe, proba-risky.

From the AL-guidance doc (adopted in the app)

  • Pre-ranked ready queue, never score the pool synchronously on label submit. ✔ predictions.parquet.
  • Rescore asynchronously after labels/retrain; store score + model version. ✔
  • Compact ranking signal over full probabilities — here the APS prediction-set size is the acquisition score and the map's uncertainty layer (one computation, two uses).
  • Benchmark each model family + output mode separately before promising latency. ✔ this report.
  • Decision rule: if a Timber change doesn't cut queue-refresh / label-to-next-item time, batching & caching matter more. ✔ — queue refresh is already 0.1 s.

Unique findings (not in the blog)

  • Timber 0.6.0 cannot represent CatBoost multiclass (vector-leaf) — the blog's untested caveat, now confirmed with the exact crash + the 160-vs-16 leaf-count evidence.
  • The binary-OvR escape hatch is numerically broken (0.50 prob error), not just slow — a leaf-indexing bug in Timber's oblivious-tree parser.
  • With XGBoost 3.2, native batch predict now beats Timber-via-Python per-sample (0.25 vs 0.64 µs) — the blog's narrow batch win has reversed on current libraries/hardware.
  • Timber on the REAL 10-class XGBoost model + tile (not the synthetic binary): compiles, but argmax disagrees 5.5% (max prob err 0.248) — 1 in 18 pixels mislabelled — and the full tile takes 184 s vs native 6.8 s (27× slower). The synthetic binary case flattered Timber on both accuracy and speed; on the real deep multiclass model it is a wrong map AND far slower. Conclusive.
  • The real dense-predict bottleneck is plain tree traversal (~6.8 s one-shot/tile); sklearn predict_proba, inplace_predict, and prebuilt-DMatrix predict are all equal — there is no wrapper trick (a "0.03 s" reading was a cached-DMatrix artifact).

6 · Why GPU XGBoost won't run here (and it's not fixable)

The app's model is now native XGBoost. The obvious "just use the GPU" acceleration is a dead end on this box — and the reason is specific, not a config slip:

A40-24Q
A vGPU profile. nvidia-smi -q → Virtualization Mode: VGPU.
VMM = 0
cuDeviceGetAttribute(VIRTUAL_MEMORY_MANAGEMENT_SUPPORTED) returns 0 — the vGPU disables CUDA Virtual Memory Management.
torch ✓
torch CUDA matmul works on the same vGPU — it uses legacy cudaMalloc, not VMM.

XGBoost 2.x+ allocates GPU memory through the CUDA VMM API (cuMemCreate / cuMemGetAllocationGranularity / cuMemMap) and probes it at GPU init. On this vGPU that probe fails: cuMemGetAllocationGranularity … CUDA_ERROR_NOT_SUPPORTED (at cuda_dr_utils.cc:92). It fails with device="cpu", with CUDA_VISIBLE_DEVICES="", and with use_rmm=True — the VMM probe runs before any allocator is consulted. (Practical fix that is needed: the default CUDA xgboost wheel even crashes on CPU init for the same reason — install xgboost-cpu, which has no CUDA code to probe.)

Alternative build that DOES use the vGPU: xgboost 1.7.6

The VMM allocator was added in XGBoost 2.0. xgboost 1.7.6 (last 1.x) predates it and uses the legacy caching cudaMalloc — torch's path. Tested on this vGPU: it works. On the real data (74k×64, n300 d6): GPU fit 8.2 s vs CPU 22.4 s — 2.7× faster training. But GPU predict is not faster (transfer overhead: 0.5 s GPU vs 0.04 s CPU predictor on the tile), and gpu_hist builds different trees than hist. Not adopted: 1.7.6 is EOL, pinning it would drag the whole shared venv back to 1.x, and the only win is fit-time — and live retrain (~10 s) isn't the bottleneck. Kept as the documented escape hatch if training time ever dominates.

8 · CatBoost vs XGBoost head-to-head (real data) — and the final pick

Because the workflow has many train cycles, we benchmarked both libraries, CPU and GPU, on the real data (74k×64, n300 d6, GroupKFold holdout). The decisive column is the 5-fold cross-conformal time (5 fits — the dominant per-retrain cost) and the dense-tile predict.

model1 fitholdout F15-fold cross-conformaldense tile predict
XGBoost 1.7.6 CPU17.6 s0.690380 s~12 s
XGBoost 1.7.6 GPU7.6 s0.687936 s~12 s
CatBoost CPU18.0 s0.689276 s~5.6 s
CatBoost GPU2.6 s0.685714.5 s0.7 s¹

CatBoost GPU wins both axes: ~3× faster training than XGBoost GPU and its symmetric-tree CPU predict is ~17× faster on a dense tile (XGBoost GPU predict is no faster than CPU — transfer overhead). F1 is within noise across all four (0.686–0.690). CatBoost GPU also sidesteps the vGPU VMM problem entirely (its own allocator), so no EOL-1.7.6 / dask baggage. ¹ 0.7 s one-shot; 5.7 s through the block-windowed raster writer (now I/O-bound, not the model).

9 · Recommendation (adopted)

CatBoost, GPU-trained / CPU-predicted, n300 d6 for the seed model, live retrain, and dense raster. Measured end-to-end after the switch: seed build 23.5 s (was 151 s on XGBoost CPU), fast retrain 4.0 s, dense tile 5.7 s (all 154 tiles ≈15 min), pool rescore 0.1 s. NYVEST_AL_DEVICE=CPU forces CPU if the GPU is busy. XGBoost is not used (2.x+ GPU can't run on this vGPU; 1.7.6 GPU works but is EOL and slower than CatBoost GPU anyway). Keep the --backend {native,timber} seam in predict_raster.py; revisit Timber only for a single-sample-latency edge deployment (its win is single-sample, never batch — and on the real multiclass model it is both 27× slower and 5.5% wrong).
